# Supported platform and helper packaging contract

<!-- platform-support-contract:v1 -->

Status: issue #13 design contract, completing criteria 1, 6 and 7. The strategy and API contract are ADR-028; this fixes the OS and filesystem matrix, the packaging and permissions, and what an unsupported environment does. Runtime implementation of the remaining boundary work stays `required_for_v1` after design gate #39.

## 1. Authority

The boundary adapter's guarantees are not portable facts. They are what specific syscalls do on specific filesystems, and a claim like "no-follow on every traversed component" is true only where the calls it rests on exist and behave.

So the supported set is enumerated rather than implied. The closed JSON Schema is `resources/platform-support/platform-support.schema.json`, and the matrix is `resources/platform-support/platform-support.v1.json`.

An environment outside the matrix does not get a weaker adapter. It gets a park, before the first side effect.

## 2. Boundaries

ADR-028 chose the strategy and the helper's API. Issue #10 owns runtime identity, into which the helper's version and digest are bound. Issue #26 owns provider capability. This contract fixes: which platforms are supported and on what evidence, how the helper is packaged and permissioned, and what happens where it is not supported.

## 3. What a supported platform means

A row in the matrix is a claim with evidence behind it, not an aspiration. Each records:

- OS and architecture;
- the filesystem families verified on it;
- the syscall family the guarantees rest on — `openat2`, `*at` plus `O_NOFOLLOW`, `RENAME_NOREPLACE`, `RenameatxNp`;
- which of the adapter's guarantees hold: no-follow per component, type check, owner check, mode check, device check, no-replace rename;
- how it is verified: CI job, manual smoke, or not verified;
- the support level.

Three levels, and the difference matters:

- **`supported`** — verified in CI on every change, all guarantees hold;
- **`best_effort`** — the guarantees hold but verification is manual or periodic. A regression here is found late, and the row says so;
- **`unsupported`** — one or more guarantees cannot be provided. The adapter refuses rather than degrading.

A guarantee listed as holding on a row with `not_verified` evidence is refused by the validator. An unverified claim is not a weaker claim; it is an unchecked one, and the two are easy to confuse in a table.

## 4. Filesystems, not just kernels

The same kernel gives different answers on different filesystems, so the matrix names them. Cases that are called out because they break assumptions rather than syscalls:

- **case-insensitive** volumes (APFS by default, exFAT): two names that differ in case are one file, so a path check that compares bytes can pass while the operation targets another entry;
- **network filesystems** (NFS, SMB): `flock` semantics and rename atomicity are not the local ones, and the project lock is exactly what depends on them;
- **overlay and container filesystems**: a rename may not be atomic across layers;
- **filesystems without `O_NOFOLLOW` support at every component**: the guarantee has no local implementation.

Where a case cannot be given, the row says `unsupported` and names the guarantee that is missing. It does not say `best_effort` and hope.

## 5. Packaging and permissions

The helper ships as three binaries beside the daemon — `bin/autosk`, `bin/autoskd`, `bin/autosk-store-lock` — built in CI for each supported platform, with the LICENSE retained. All three run as the installing user (`binaries_run_as=installing_user`), autoskd among them: what autoskd writes, the installing user's account writes (§5a). The ref-custody helper, which is not one of them, runs as the installing user too (§5a), and a model process autoskd starts runs in an account of its own (§5b).

- **permissions**: the helper is executable and owned by the installing user; it is never setuid, never setgid, and never installed into a world-writable directory. A world-writable install directory is a park reason, not a warning, because anything there can be replaced between the check and the run;
- **install**: the helper's digest is recorded at install and bound into runtime identity (#10). A helper whose digest does not match the recorded one is refused;
- **upgrade**: a new helper is a new digest, and therefore a new runtime identity. Tasks pinned to the old one are not silently migrated — that is #10's migration path, not a packaging detail;
- **rollback**: the previous helper and its digest remain available until retention ends, so a rollback is a pin change rather than a rebuild;
- **the digest is checked before each launch and the launched binary is the one that was checked** — a SHA taken before `exec` does not close the replacement window on its own, which is stated here rather than claimed away. The narrowing is that the daemon holds the helper open for the life of the project (ADR-028), so the window exists once per project rather than once per operation.

## 5a. The ref-custody helper and the project's Git directory

The ref-custody helper of 02 §2, `autosk-flow-ref-custody` (#5, `src/git/ref-custody-helper.ts`), is the only code that writes a ref under `refs/autosk/**` — the Epic's planning, candidate, audit and staging refs (ADR-095) — or that ref's reflog. It runs as the installing user, as §5's binaries do, and it is not one of them: a separately shipped executable, not one of §5's installing-user binaries, and not a fourth binary beside the daemon, run as a process of its own with its own project-scoped Unix socket, request intents, journal and nonces, and registered as the installing user's launchd agent on macOS or systemd user unit on Linux. Its socket accepts only the daemon capability and checks the peer with `getpeereid` or `SO_PEERCRED`. ADR-102 withdrew the service account ADR-095 gave it, and the privileged custody install with it: the narrow re-review of the first account model measured that a Git directory two accounts write either locks the principal out of their own repository or makes the helper trust files the principal writes. It is an install record of its own, `install.ref_custody_service` in the matrix, whose constants the schema holds:

- **who runs it**: the installing user (`runs_as=installing_user`, `runs_as_installing_user=true`), with no administrator step (`bootstrap`, `requires_administrator=false`): its bootstrap registers it, closes the project's Git directory to every other account (mode `0700`), migrates protected packed refs to loose form, pins `gc.packRefs=false` and the planning refs' reflog retention (`epic-planning-ref.md`), turns on per-worktree configuration (`extensions.worktreeConfig`, §5b) and records the bootstrap receipt the ref-custody policy digest binds;
- **whose the Git directory is**: the installing user's (`git_directory_owner=installing_user`) — an ordinary repository, with no service owner, no group-writable Git directory, no sticky bit and no `safe.directory` exception, and the user's porcelain works on it as on any repository: deleting branches and tags, `git config`, hooks, `fetch --prune`, `gc` (measured with Git 2.43). The model account of §5b opens no Git directory of the project, for reads or for writes;
- **who writes what, by protocol**: the helper alone the protected paths — every ref under `refs/autosk/**` and its reflog (`protected_paths`) — and the installing user's account, autoskd's and the principal's, everything else: objects, ordinary refs and each worktree's `HEAD` and index (`git_directory_writers`). The target ref is the daemon's `integrateApproved`'s to move;
- **what keeps a protected ref where the helper left it** (`protected_ref_guard`): against a model, the OS — the model account writes no Git directory of the project, for every ref and not only the protected ones; against the installing user's own tools, which the OS does not stop, detection, as for the target (ADR-099). Every helper action is an expected-old compare-and-swap under its journal, so a protected ref the helper finds where it did not leave it is never overwritten or adopted, and the flow parks: a planning ref with `planning_ref_foreign_movement`, a candidate keepalive or audit ref with `planning_candidate_keepalive_invalid`, a staging ref with `receipt_missing` at `apply_staging` when its lineage carries a commit no receipt covers, and with `staging_moved_after_pass` once its aggregate PASS is recorded. A protected entry in `packed-refs` — `git pack-refs --all` writes one even with `gc.packRefs=false` (measured) — is refused by the helper's preflight before every request (`packed_refs_drift`), which parks `planning_ref_capability_missing`. A move of the target by anything but `integrateApproved` is foreign movement, detected at the CAS, which parks `foreign_movement` at `integration_recovery` (ADR-088, ADR-099). One such stop has no row yet: a staging ref the user's tool moves back to a commit its receipts cover, before the next apply, is refused by the delta driver (`foreign_ref_movement`, `approved-delta.md`) and by the helper's compare-and-swap, and none of the four parks at `apply_staging` names it; which stop takes it, under one name and one producer, is debt 12g's (R8-9's missing edge) with #18;
- **how it and autoskd run Git**: with the Git directory named explicitly, no inherited Git variable, hooks and `core.fsmonitor` off, and `--no-replace-objects`, so a replace ref the user writes changes nothing they read — measured with Git 2.43: after `git replace`, `rev-parse <commit>^{tree}` answered the replacement's tree, and with `--no-replace-objects` the true one (`epic-planning-ref.md`);
- **its identity**: pinned by the ref-custody policy digest (`docs/contracts/epic-planning-ref.md`), which carries the packaging signature and the generation-bound upgrade and rollback rules.

Instead of §5's checks — installing-user ownership, the recorded binary digest bound into runtime identity, and the per-launch digest check — the helper is checked through the ref-custody policy: its packaging fields name the executable and its signature, the bootstrap receipt records the account it runs as and the Git directory's pins, and every helper request carries the policy digest, so a helper that is not the pinned one refuses before any Git write. The policy schema has no closed field for the helper executable's digest and path yet; that field, and the check that reads it at launch, are open for #5 and #13.

The ref-custody policy admits this: its schema (`ref-custody-policy.schema.json`) takes an optional `helper_runs_as=installing-user`, under which each platform profile's `helper_account` and `owner_account` are `installing-user` and `gitfile_read_only` is false — a model can replace its worktree's gitfile (§5b) — the packed-refs policy's `maintenance_owner` is `installing-user`, and the one topology entry is the project's common Git directory at mode `0700`. The permission probes keep their actor, `project-account`, which under this profile is the model account, and their `denied` protected-ref operations. The committed example has no `helper_runs_as`: it predates ADR-102 and records the service accounts ADR-102 withdrew. Its `policy_digest` is computed over the example alone and carried by the committed signed wire goldens, so it changes only when #5 signs those goldens again — every golden is signed by the daemon key the example binds, whose private key is not in this repository (`epic-planning-ref.md`) — and the schema keeps it valid. `validate:platform-support` holds both: the committed example and its ADR-102 form validate, and a policy that mixes them does not.

Other documents name these accounts differently. The ref-custody policy's `project-account` is the model account (§5b); its `helper_account` and `owner_account`, in the committed example, are the service accounts ADR-102 withdrew; and the extension runs inside autoskd, in the installing user's account.

§5a does not cover the ADR-023 signer boundary: whether the signer runs in a separate account or a hardware enclave is declared and probed (ADR-090), and its install record is still open, owned by #4 and #34.

#5 owns the helper, #13 the install that bootstraps it; `validate:platform-support` requires both to be `required_for_v1` records of the program matrix whose implementation obligation names `autosk-flow-ref-custody`. A project whose helper and pins are absent or not proven parks `ref_custody_unavailable` at project open, before any trusted write; the host never falls back to writing a protected ref itself. That park has no producer yet, like every reason of §7, and its evaluator is named rather than built: the doctor check `security.ref_custody` (`checked_by`), which the dispatch gate requires of every workflow whose first step reaches a step that asks the helper — the steps the graph's `planning_ref_capability_missing` row parks at, which `autosk-planned`, `autosk-quick` and `autosk-ticket` reach (`CUSTODY_STEP_CHECKS`, derived as the model-step checks are). It checks the helper's process, its socket and journal and the repository's pins, and answers `unverifiable` until the probe of #13 with #5 exists; with the probe, one it cannot prove is a `fail` carrying `park_reason: ref_custody_unavailable`. The probe and the park at project open are #13's with #5 (ADR-102).

## 5b. The model account

A model process is not the installing user either. Every process autoskd starts to run a model step — `claude-agent`'s and `pi-agent`'s among them, which the pinned series starts as autoskd's children under autoskd's uid (patch `0028`'s `autoskEnv`; no patch drops a uid) — runs under a dedicated unprivileged account, `autosk-model`, which the privileged install creates — the one administrator step of this design, since the ref-custody helper of §5a needs none. autoskd keeps running as the installing user with §5's other binaries (`binaries_run_as=installing_user`): the installing user stays the principal, the account autoskd and the user's own tools run in, and the model processes are the ones kept out of it. It is an install record of its own, `install.model_account`, whose constants the schema holds:

- **who runs it**: `autosk-model`, never the installing user (`runs_as_installing_user=false`), created by the privileged install (`created_by=privileged_install`) — the one administrator step of this design (`privileged_install`, `requires_administrator=true`) — together with the worktree group through which it writes its worktrees' files, whose other member is the installing user;
- **how a model process starts under it**: autoskd starts it (`launched_by=autoskd`) through a narrowly scoped mechanism the privileged install sets up — a sudoers rule limited to the pinned model runtimes, or to the one supervisor that starts them (below), or a service-manager unit (`launch_mechanisms`) — never a setuid or setgid binary of this project (`setuid_binary=false`): §5's prohibitions stand, and #13's implementation picks the mechanism per platform;
- **how it is stopped**: autoskd cannot signal a process of another uid — `kill(2)` needs the same uid or `CAP_KILL` — so the launch mechanism gives autoskd whole-tree termination: a timeout kills every process a launch started and all their descendants, and no orphan survives (`whole_tree_termination=true`, as `docs/contracts/provider-preflight.md` §4 requires of every driver). A service-manager unit whose control group the manager kills as a whole satisfies it. A sudoers rule alone does not: measured with sudo 1.9.15p5 under `Defaults use_pty`, a SIGTERM to sudo ended the command it started, while a background child in the command's process group and a descendant that called `setsid` kept running. With a sudoers rule, the rule starts a single supervisor under the model account, which starts each model runtime as its own descendant, keeps each tree in a control group or process tree it can signal, and kills a tree whole when autoskd asks;
- **what it may write**: its worktree and a session directory of its own that holds its provider session and each runtime's `HOME` and configuration (`writes`). autoskd creates the worktree as the installing user under umask `007`, so its root and every directory in it are the installing user's, setgid for the worktree group and group-writable (`2770`), and the checked-out files are `0660`; the model edits them and creates files and directories of its own, and autoskd pins the worktree's gitfile at `0644`, so the model cannot rewrite it in place, but it can replace its worktree's gitfile, which neither autoskd nor the helper reads (measured with Git 2.43). It opens no Git directory of the project, common or per-worktree, for reads or for writes (`git_directory_writes=false`, `git_directory_reads=false`): the Git directory's root is closed to it (§5a), so its own `git` in its worktree finds no repository (measured), it moves no ref, the target's included, and what a model step needs from the project's history the launch path hands it (#18). It writes nothing under `.autosk`, whose store accepts a file only when it is private to autoskd's uid (the store helper's `ownership` refusal) and which README rule 16 keeps from model sessions;
- **what it cannot reach**: the signer's endpoint and the secure store (ADR-023; `signer_access=false`, `secure_store_access=false`), the installing user's keychain and accessibility grants (`keychain_access=false`), and the installing user's processes, which a different uid cannot ptrace. It holds no daemon capability (`daemon_capability=false`) — no `AUTOSK_SESSION_TOKEN`, no step capability — and cannot use autoskd's RPC: its token (`~/.autosk/daemon-token`, `0600`, in the installing user's home) and its Unix socket are the installing user's, and its TCP listener binds loopback only — upstream's default without `--tcp`, `0.0.0.0:7077`, is never how an install that launches models runs it — so a model process that reaches the listener holds no token. It answers only through its session's own tools; what the daemon's custody refuses (ADR-025) it cannot do by another route;
- **what autoskd does with what it writes**: autoskd never discovers a repository from a directory the model account can write. Every Git command it runs for a model worktree names the per-worktree Git directory and the work tree (`--git-dir`, `--work-tree`), turns hooks, `core.fsmonitor` and submodule recursion off on its command line (`-c core.hooksPath=/dev/null -c core.fsmonitor=false -c diff.ignoreSubmodules=all`) and inherits no Git variable, so a gitfile or `.git` a model plants in its worktree or in a submodule path is never followed. Measured with Git 2.43: named explicitly, Git read the true state and ran neither the planted repository's fsmonitor nor its hook; discovering from the worktree, Git refused the model-owned gitfile as dubious ownership. An explicit `--git-dir` skips that ownership check, so autoskd names only the per-worktree Git directories it recorded. The installing user's own Git needs no `safe.directory` exception: a model worktree's root, gitfile and administrative directory are the installing user's, so the user's Git discovers the worktree, and a gitfile the model plants there is refused as dubious ownership (measured). Every model worktree's `config.worktree` pins `core.hooksPath=/dev/null` and `core.fsmonitor=false`, so the user's own porcelain there runs no hook a model wrote — measured: with the project's `core.hooksPath=.husky`, the user's `git commit` in a model worktree ran the model's hook as the user without the pin, and not with it. What the pin does not reach is an implicit bare repository a model builds inside a directory the user checked out: that directory is the user's, so Git's ownership check passes, and the user's `git diff` there ran the model's `diff.external` as the user (measured); `safe.bareRepository=explicit` refuses it (measured). README therefore advises `safe.bareRepository=explicit`, and never a `safe.directory` exception for a model worktree, `*` least of all. The aggregate driver already holds the rule for its throwaway checkout, where the checks run model-written code: it reads the checkout back from the repository's own record of its worktrees — the one new worktree, at the checkout's real path and the staging commit, read from NUL-terminated porcelain — and the tree of the staging commit, and runs no Git command from inside the checkout (`checkoutStaging`). A session file autoskd reads from a model's session directory is untrusted input, parsed and copied, never adopted into autoskd's store as its own file. A check that runs the project's own code — aggregate verification's checks among them — runs content models wrote, so it runs under the model account like a model step, never as the installing user.

That account is the model sandbox 03 §5 and 02 §5 rest on (ADR-023), with an owner. Being another uid, it inherits neither the installing user's keychain nor any file only that user may read, so a provider credential the user holds reaches a model process only as its launch hands it. What another uid does not isolate is named: a model process reads what every account may read — a file the user left readable to all, the command line of every process in `/proc` unless `/proc` is mounted with `hidepid`, a shared `/tmp` — and every model process runs under the one account, so one model process can signal or ptrace another. That isolation, between the models, stays the daemon's — worktrees, sessions, custody — and a per-process OS sandbox is outside matrix v1 (#197 proposes one). Where each model's worktree and session directory lie under the project's canonical root — so that the cross-project guards of 02 §5 still hold, every directory above them lets the model account through and no further, and the account writes those and nothing else of the installing user's — is open for #13 with #18 and #11: 02 §5 puts the external worktree cache under the installing user's home and provider sessions under `.autosk/autosk-flow/provider-sessions/`, and neither placement is one the model account can use.

#13 owns the account, its group and the launch mechanism the privileged install sets up, whole-tree termination included, and the probe that proves them: run as the model account, it proves the account opens no Git directory of the project, reaches neither the signer's endpoint nor the secure store, cannot read autoskd's RPC token and finds autoskd's TCP listener, where there is one, only on loopback, and that the launch mechanism kills a model process tree whole. #11 owns the model process environment — started under the account, with no daemon capability, no session token, and its `HOME` and configuration in its own session directory; #18 the launch path, which starts every model process and every check that runs model-written code under the account, only through the dispatch gate, kills a timed-out tree whole through the mechanism, creates each model worktree with the modes and `config.worktree` pins above, hands a model step what it needs from the project's history, and runs Git for a model worktree only with its directories named. `validate:platform-support` requires all three to be `required_for_v1` records of the program matrix whose implementation obligation names `autosk-model`. The record's check is `security.model_account` (`checked_by`), which every workflow that runs a model step requires (`MODEL_STEP_CHECKS`); it answers `unverifiable` until #13's probe exists, so no model workflow starts on an account nobody checked (ADR-102).

## 6. Unsupported environments park before the first side effect

The check runs at project open, before any trusted write. It does not run after the first failure, because by then the side effect has happened and the park is a report rather than a prevention.

Parking names the platform, the filesystem, the missing guarantee, and what the operator can do. "Unsupported environment" alone is not a park reason.

## 7. Park reasons

Closed set: `unsupported_platform`, `unsupported_filesystem`, `missing_guarantee`, `world_writable_install`, `helper_digest_mismatch`, `helper_not_executable`, `setuid_helper`, `unverified_claim`, `ref_custody_unavailable`.

None of these reasons has a producer yet: no code in this repository parks any of them, and the checks at project open that will are #13's implementation. `ref_custody_unavailable` has its evaluator named, the doctor check `security.ref_custody` (§5a), which answers `unverifiable` until the probe of #13 with #5 exists.

## 8. Required implementation tests

- each supported row exercised in CI on its platform;
- a case-insensitive volume where two names differ only in case;
- a network filesystem where `flock` semantics differ;
- an overlay filesystem where rename is not atomic across layers;
- a world-writable install directory;
- a setuid helper binary;
- a helper whose digest does not match the recorded one;
- an unsupported platform parking before any trusted write;
- an upgrade producing a new identity, and a rollback restoring the old pin;
- a project with no proven helper or pins parking `ref_custody_unavailable` before any trusted write; the installing user's porcelain — branch and tag deletion, `git config`, `fetch --prune`, `gc` — working on the project's Git directory after the bootstrap; and a protected ref the user's own tool moves, or packs with `git pack-refs --all`, found at the helper's next request and parked under the stop §5a names, never overwritten or adopted;
- a process under the model account failing to open any Git directory of the project, for reads or for writes, to reach the signer's endpoint, the secure store or the installing user's keychain, to read autoskd's RPC token, and to ptrace the installing user's processes, and finding autoskd's TCP listener, where there is one, only on loopback; and no model process starting where the model account or its launch mechanism is absent;
- a model process tree that forks, double-forks and leaves its session killed whole on a timeout through the launch mechanism, with no process of the model account outliving the launch it came from;
- a gitfile or `.git` a model plants in its worktree, or in a submodule path of it, never followed by a Git command autoskd runs, and no hook or fsmonitor of the planted repository running; and a check that runs the project's code running under the model account;
- a model worktree's gitfile the model replaced refused by the installing user's Git as dubious ownership, a hook the model writes under a project `core.hooksPath` not run by the user's porcelain in its worktree, and a bare repository the model builds in a checked-out directory refused under `safe.bareRepository=explicit`.
